# airtw 年度資料包的格式

> 實測自全部 44 個年度包（1982–2025，共 3.41 億筆觀測）。
> 由 `describe_archive()` 逐檔掃描與 `twair qc report` 全量統計產生，不是照文件抄的。

## 最重要的一件事：格式不是照年代演進的

我一開始假設格式隨年代單調演進（舊 → 新）。**這個假設是錯的。**
實際掃描結果顯示容器格式與小時欄標號**來回跳動**：

| 年份 | 容器 | 資料檔格式 | 編碼 | 小時欄標號 | 測站數 |
|---|---|---|---|---|---|
| 1982 | zip | ODS + XLS | XML | **1–24** | **1** |
| 1983 | zip | ODS + XLS | XML | 1–24 | 5 |
| 1984–1985 | zip | ODS + XLS | XML | 1–24 | 10 |
| 1986 | zip | ODS + XLS | XML | 1–24 | 17 |
| **1987** | zip | **XLS only（無 ODS）** | **BIFF** | 1–24 | 17 |
| 1988–1989 | zip | ODS + XLS | XML | 1–24 | 17 |
| 1990–1991 | zip | ODS + XLS | XML | 1–24 | 18 |
| 1992 | zip | ODS + XLS | XML | **1–24** | 18 |
| 1993–1995 | zip | ODS + XLS | XML | **00–23** | 70–71 |
| 1996–2007 | zip | CSV | **Big5/cp950** | **1–24** | 71–78 |
| **2008** | zip | **ODS + XLS** | XML | **1–24** | 77 |
| 2009–2011 | zip | CSV | **Big5/cp950** | **1–24** | 77–78 |
| 2012 | zip | ODS + XLS | XML | **1–24** | 76 |
| 2013–2017 | zip | ODS + XLS | XML | **00–23** | 76–77 |
| 2018–2023 | zip | CSV | **UTF-8 BOM** | **00–23** | 77 |
| **2024** | **7z** | CSV | UTF-8 BOM | 00–23 | 77 |
| 2025 | zip | CSV | UTF-8 BOM | 00–23 | 77 |

四個具體反例，任何一個都足以推翻按年份分派的做法：

1. **2008 是 CSV 年代中的 ODS 孤島。** 1996–2007 是 CSV、2008 是 ODS、2009–2011 又回到 CSV。
2. **小時欄標號獨立於容器翻轉。** 1992（ODS）是 1–24，1993（也是 ODS）是 00–23；
   2012（ODS）是 1–24，2013（也是 ODS）是 00–23。
3. **2024 是 7-Zip，但下載連結的副檔名仍是 `.zip`。** 只看副檔名會直接爆掉。
4. **1987 只有 XLS，沒有 ODS。** 其餘所有 ODS 年份都同時提供兩種格式，只有這一年例外。
   若照「有 ODS 就讀 ODS、否則跳過」的邏輯，1987 整年會靜默消失。

因此 `twair.ingest.archive` **一律從檔案自身的表頭與 magic bytes 偵測格式**，
不查年份對照表。`detect_dialect()` 對無法辨識的標號直接拋錯，而不是猜。

## 小時欄標號 1–24 的位移陷阱

官方 ReadMe 明載：

> 0時：指 0:00-0:59，2時：指 2:00 - 2:59…，23時：指23:00-23:59

所以在 1–24 標號的檔案裡，**標為 `1` 的欄位是午夜 00:00，不是凌晨 1 點**。
弄錯會讓 1996–2012 這 17 年的資料整批位移一小時。
`tests/test_archive.py::TestLegacyBig5Generation::test_hour_one_column_lands_at_midnight`
就是釘住這件事的迴歸測試。

## 旗標語意在世代間改變

| | 舊格式（CSV Big5 / ODS） | 新格式（CSV UTF-8） |
|---|---|---|
| 形式 | 數值**後綴**：`15#`、`0.1#` | **整格取代**：`#` |
| 無效值的原始測值 | **保留** | **遺失** |

這代表**同一套缺漏填補策略在新舊年代的效果不同**。
長期趨勢分析必須對此做敏感度檢驗；`value_retained` 欄位就是為此而存在。

**但這個「舊保留、新丟棄」的二分法只對了一半** —— 見下方全量實測結果。

## 官方旗標定義

逐字取自資料包內附的 `ReadMe_普通測站20170301.odt`：

| 符號 | 官方定義 |
|---|---|
| `#` | 表示儀器檢核為無效值 |
| `*` | 表示程式檢核為無效值 |
| `x` | 表示人工檢核為無效值 |
| `NR` | 表示無降雨 |
| 空白 | 表示缺值 |

### legend 未涵蓋者

實測另外出現，官方文件沒寫：

- `NA`、`A`（新格式）
- **複合標記** `NA#`（2023 年出現 87 次）、`NA*`、`NR#` 等
- **`-99#`**（1987 XLS）：`-99` 是舊式無資料哨兵值，且一律帶 `#` 旗標。
  因為旗標已判定為無效，`-99` 不會進入有效資料；值域檢查也會攔下。
  但這說明**早期年份用數值本身表達缺值**，與後期用旗標表達不同。

本專案的處理原則：**無效判定優先於語意註記**。
`NA#` 視為無效，而非「不適用」。見 `conf/qc.yaml`。

## XLS（BIFF）格式的額外處理

1987 的 XLS 檔與其他格式有三處不同，都會靜默出錯：

| 項目 | 情況 | 處理 |
|---|---|---|
| 日期 | **Excel 序號**（`31778.0`）而非字串 | `xlrd.xldate` 轉為 `YYYY/MM/DD` |
| 數值 | 型別化的 float（`15.0`） | 整數還原為 `"15"`，避免下游把 `"15.0"` 當文字 |
| 工作表 | 名為 `查詢小時值` | 取第 0 張工作表 |

小時欄標號為 **`01`–`24`**（補零），整數化後為 1–24，
因此與 Big5 CSV 世代共用同一套位移修正。

### 保留率其實不是照世代分的（全量實測後修正）

上表的「舊格式保留、新格式丟棄」在全量資料上**只對了一半**。
逐年實測 44 年的無效值保留率：

| 年份 | 世代 | 保留率 |
|---|---|---|
| 1982–1994 | ODS / XLS | 1.000 |
| **1995** | ODS | **0.818** |
| 1996 | Big5 CSV | 1.000 |
| **1997** | Big5 CSV | **0.000** |
| **1998** | Big5 CSV | **0.340** |
| 1999–2000 | Big5 CSV | 1.000 |
| **2001** | Big5 CSV | **0.000** |
| 2002–2017 | Big5 CSV / ODS | ≈1.000 |
| 2018–2025 | UTF-8 CSV | 0.000 |

**1997 和 2001 完全不保留測值，1998 只保留 34%，1995 保留 82%**——
這些都是「舊格式」年份。也就是說旗標慣例**在同一個世代內逐年變動**。

實務結論：`value_retained` **必須逐年實測，不能從 generation 推論**。
任何跨年度的缺漏填補敏感度分析都要用實際保留率，而不是「2018 前後」這種粗分。

## 🚨 風向哨兵碼 —— 實測結果與初判不同

同一份 ReadMe 明載：

> 風向資料 **888 代表無風，999 則代表儀器故障**。

這是真實存在的陷阱：把風向當一般線性變數丟進迴歸，888 會被當成「888 度」參與運算。

**全量 44 年實測後，結論確定：哨兵碼只存在於 1993–2004 這 12 年。**

| 期間 | 哨兵碼出現率 |
|---|---|
| 1982–1992 | **0%**（11 年，完全沒有） |
| 1993 | 2.62% |
| 1994–2003 | **4.6% – 6.4%**（1998 年最高 6.41%） |
| 2004 | 3.11% |
| **2005–2025** | **0%**（21 年，完全沒有） |

也就是說：**2018 年畢業專題使用的 2010–2017 區間，哨兵碼出現次數為零。**

我在 Phase 0 把這列為原專題的重大缺陷，**這是過度推論，現已由全量資料否證**。
它是 1993–2004 年資料的真實陷阱，但與原專題無關。

> 但另一項判斷不變：即使沒有哨兵碼，對風向這種 **circular variable**
> 取算術平均本身仍然是錯的（0° 與 359° 平均得到 179.5°，正確答案是 359.5°）。
> 原專題的月平均風向從根本上不可解釋，這一點與哨兵碼無關。

哨兵處理實作於 `twair.qc.sentinels`，值改為 null 並標記為 `calm` / `instrument_fault`，
且**不覆寫環境部已判定為無效的格位**——官方判定比我們的推論更權威。

## 其他觀察

- **2015 年的資料包裡有一個 `.exe`。** 本專案只讀 `.csv` / `.ods`，
  從不執行也不解壓任何可執行檔，但值得記錄。
- **`.txt` 檔**廣泛存在於 1996–2011 的資料包（每包 8 個），
  推測是分空品區的 ReadMe，待確認是否含逐年不同的 legend。
- **`.doc` / `.odt`** 是說明文件，非資料。
- **ODS 與 XLS 內容相同**，本專案優先讀 ODS（純 XML，無需二進位試算表讀取器）。
- **2011 年格式變更**：官方 ReadMe 提到「自 2011 年起由每日依監測項目多筆排列之順序
  修正為每日一筆資料呈現所有監測項目排列方式」。
- **PM2.5 小時值的使用限制**：「PM2.5 自動監測尚無標準方法，其小時值僅供預警參考，
  不宜直接與 PM2.5 空氣品質標準之 24 小時值（35 微克/立方公尺）比較」，
  測量方法為貝他射線衰減法。原專題未提及此限制。

## 測站網的時變性

測站數從 1992 年的 **18 站**成長到 1999 年的 **84 站**，
之後穩定在 76–78 站。1999 年的站數甚至多於 2018 年以後。

跨年度比較「全台平均」時必須考慮測站組成變動，
否則趨勢會混雜「監測網擴張」與「空氣品質變化」兩件事。
這是原專題完全沒有處理、而終極版必須明確建模的問題。

### 測站類型（1994 年 ReadMe 所載）

| 類型 | 站數 | 測站 |
|---|---|---|
| 一般空氣品質監測站 | 60 | |
| 工業空氣品質監測站 | 5 | 頭份、線西、麥寮、台西、前鎮 |
| 交通空氣品質監測站 | 6 | 鳳山、三重、中壢、永和、復興、大同 |
| 國家公園空氣品質監測站 | 2 | 恆春、陽明（恆春兼一般測站） |
| 背景空氣品質監測站 | 4 | 萬里、觀音、三義、橋頭（萬里、三義兼一般測站） |
| 參考測站 | 2 | 關山、埔里 |

原專題因「五種類別測站測項不同」而只採用共通測項。
本專案改為**把測站類型當作模型變數**——交通站與背景站的
PM2.5 驅動因子本來就應該不同，這是資訊而非雜訊。

## 空品區

1992–2017 為 7 區（中部、北部、宜蘭、竹苗、花東、雲嘉南、高屏），**無離島**。
2018 年起為 8 區（增加離島）。

## 下載端的兩個陷阱

1. **Google Drive 配額限流。** 連續抓取數十個檔案後會回
   「Cannot retrieve the public link ... or have had many accesses」。
   這是速率限制不是永久失敗，`--patient` 會以 60/180/420/900 秒退避重試。
2. **失敗時回傳 HTML 而非錯誤狀態碼。** 因此下載後一律以 magic bytes
   驗證是 zip 或 7z，不是就刪除並回報失敗。

## 監測網的起點

1982 年**全台只有 1 個測站**，1983 年 5 站，1984–85 年 10 站，1986 年起 17 站。
真正接近 70 站的規模要到 1993 年。

這代表 1982–1992 的「全台平均」在統計上幾乎沒有意義，
但這段資料仍有價值：它記錄了個別測站的長期序列，
可用於單站趨勢分析與監測網擴張本身的研究。

### 歷年旗標定義變更結論

經全量實測 44 個年度原始檔案包（1982–2025 年），品質旗標的符號定義在跨年度間**無任何改變（no change found）**。所有存在說明文件的年份（1991–2017 年）中，官方記載之有效與無效旗標符號均一致為 `#`（儀器檢核無效）、`*`（程式檢核無效）、`x`（人工檢核無效）、`NR`（無降雨）與 `空白`（缺值）。1982–1990 年與 2018–2025 年之資料包內未包含 ReadMe 說明文件。據此，基於 2017 年參考文件所建置之品質旗標解析器，對所有歷史年代之旗標符號定義均完全適用。

**但風向哨兵碼的語意存在一處跨年差異。** 2001 年說明檔將 `888`（風向不定）與 `999`（靜風）直接寫入「普通測站資料註記說明」欄位中；2017 版（及 2012–2017 ODT）則於內文記載 `888` 代表無風、`999` 代表儀器故障。兩者對 `999` 的定義不同（靜風 vs. 儀器故障）。本專案現行哨兵處理（`twair.qc.sentinels`）採用 2017 版定義（888→calm、999→instrument_fault），此處記錄差異供日後評估。
